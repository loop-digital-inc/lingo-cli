# Lingo CLI

Keep a codebase's locale files in step with a Lingo project.

```bash
npx lingo add "Pay now"   # add a key for new text: brave_otter_jump
npx lingo push            # send the keys you added while developing
npx lingo pull            # take what translators wrote
```

Lingo stays the place where translations are edited. `lingo pull` writes them as the locale files your app already reads, so nothing changes at runtime; `lingo push` sends the keys you add in code, however you name them (hand-written, or generated by a tool such as Sherlock).

## Setup

1. Install it as a dev dependency:

   ```bash
   npm install --save-dev @loop-digital/lingo
   ```

2. Create `lingo.config.json`:

   ```bash
   npx lingo init
   ```

   In a Paraglide project the output path is taken from `project.inlang/settings.json`.

3. In Lingo, open your project → **Settings → API keys** and create a key. Put it in the environment as `LINGO_API_KEY`, or in a `.env` file next to the config. Keep it out of git.

4. Pull:

   ```bash
   npx lingo pull
   ```

## Commands

| Command | What it does |
| --- | --- |
| `lingo init` | Creates `lingo.config.json`. Leaves an existing one alone. |
| `lingo pull` | Downloads translations and writes one file per locale. Files that are already up to date aren't touched. |
| `lingo pull --check` | Writes nothing; exits with status 1 when a file is missing or out of date. For CI. |
| `lingo push` | Sends the locale files to a Lingo branch. Adds new keys and the values Lingo doesn't have yet; changes nothing that's already there. |
| `lingo push --overwrite` | Also replaces values in Lingo that differ from your files. |
| `lingo push --dry-run` | Shows what a push would change, and saves nothing. |
| `lingo add "<text>"` | Adds a key for new text to a Lingo branch and to the default locale's file. Its name is random, like `brave_otter_jump`, and unused anywhere in the project. |
| `lingo add "<text>" --key <name>` | Same, with the name you choose (`-k` for short). |
| `lingo unused` | Lists keys in the locale files that your code doesn't use. Exits with status 1 when it finds any. |

`--branch <name>` picks the Lingo branch for `pull`, `push` and `add`. `--config <path>` uses another config file. `--help` and `--version` do what they say.

## Branches

Every push and pull is against one Lingo branch:

| | `--branch` or `"branch"` given | Neither given |
| --- | --- | --- |
| `lingo pull` | that branch | the project's default branch |
| `lingo push` | that branch | the project's default branch |

Each branch decides what it allows, in the project's settings in Lingo. A push needs a branch that allows importing, and a pull one that allows exporting. A main branch is often locked so it only changes through approved syncs; then push to a feature branch:

```bash
npx lingo push --branch feature/checkout
npx lingo pull --branch feature/checkout
```

Setting `"branch": "feature/checkout"` in the config does the same for both, and a release build can still run `lingo pull --branch main`.

## Adding keys

```bash
npx lingo add "Pay now"
# Added brave_otter_jump to branch main and messages/en.json
```

Then use it in code, such as `m.brave_otter_jump()` with Paraglide, and translate it in Lingo. Like the Sherlock VS Code extension, the name is a random phrase: easy to say and to search for, and it doesn't go stale when the text changes.

- **No clashes, now or later.** A random name is checked with Lingo first and is unused on every branch, deleted keys and branches in the trash included. Branches match keys by name when they're compared or synced, so a key added on one branch won't collide with another branch's key when they meet. (Two people would have to draw the same name from over a million in the same moment.)
- **Your own name:** `--key checkout.pay_now`. It only has to be new on the branch, as when a key is added in Lingo. If another branch has a key by that name, you're warned, since syncing those branches treats the two as one key.
- **Saved in Lingo first.** The key is created on the branch before the file is written, so nobody else can take the name in between. That needs a key with write access and a branch that allows importing, as for `lingo push`.
- **Only the default locale's file changes.** Translations come in with `lingo pull`.

## Finding unused keys

```bash
npx lingo unused
```

This reads only local files: no API key, and nothing is changed or deleted. A key counts as used when its name appears as a whole word in your source, however it's written — `m.save_button()`, `t('cart.title')`, `key="save_button"` — so it works with any framework.

- **Where it looks:** the folders in `"source"` (default `src`), in code and markup files. In a git repository, files git ignores are skipped, which leaves out generated code such as Paraglide's compiled messages.
- **What it can't see:** keys put together at runtime, like ``m[`status_${name}`]``. List those under `"ignoreKeys"`, where `*` stands for any text: `["status_*"]`.
- **Removing them:** delete the keys in Lingo, then `lingo pull`. A push never deletes, so removing them from the files alone doesn't remove them from Lingo.

## Configuration

`lingo.config.json`:

```json
{
	"output": "messages/{locale}.json",
	"format": "paraglide",
	"branch": "main",
	"locales": ["en", "fr"],
	"source": ["src"],
	"ignoreKeys": ["status_*"]
}
```

| Field | Meaning | Default |
| --- | --- | --- |
| `apiUrl` | Where Lingo's API is. Only needed for another address, such as a staging server; `lingo init --api-url <url>` saves it. `LINGO_API_URL` overrides it. | `https://api.lingo.io` |
| `output` | Where each locale's file goes, relative to the config file. Must contain `{locale}`. | `messages/{locale}.json` |
| `format` | `paraglide` for the [inlang message format](https://inlang.com/m/reootnfj/plugin-inlang-messageFormat) Paraglide JS reads, or `mf2` for MessageFormat 2 as Lingo stores it. | `paraglide` |
| `branch` | The Lingo branch to pull from and push to. `--branch` overrides it. | see [Branches](#branches) |
| `locales` | Locale codes to pull and push. | every locale |
| `source` | Folders `lingo unused` searches, relative to the config file. | `["src"]` |
| `ignoreKeys` | Keys `lingo unused` never reports. `*` stands for any text. | none |

The project isn't named in the config: an API key belongs to one project, and reaches only that one.

| Environment variable | Meaning |
| --- | --- |
| `LINGO_API_KEY` | A project API key. Read from `.env.local` or `.env` in the current folder when not already set. |
| `LINGO_API_URL` | Overrides `apiUrl`. |

## Good to know

- **Commit the files `lingo pull` writes.** Your build then never depends on Lingo being reachable.
- **Pushing needs a key with write access.** Keys are read-only unless created as "Read and write". Deleting a key in Lingo revokes it at once.
- **A push never deletes.** Keys you remove from your files stay in Lingo; delete them there.
- **Pushed values need review.** New and changed values arrive in Lingo marked "Needs review".
- **Locales aren't created by a push.** A file for a locale the project doesn't have is refused; add the locale in Lingo first.
- **Values that can't be converted are left out and listed,** in both directions. Paraglide has no markup, for example; such a value is reported and the rest go through.
- **Indentation is kept.** A file that already uses spaces stays that way; new files use tabs.

## Development

```bash
npm install
npm test          # runs the TypeScript sources directly; needs Node 22.18 or newer
npm run check     # type-check
npm run build     # compile to dist/
node src/cli.ts pull
```
